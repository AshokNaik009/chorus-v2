# bench/RESULTS.md — render scaling

Generated by `node bench/dist/render-scale.js`. Every number below is measured, not
estimated, and not rounded in our favour.

## Conditions

- Outer terminal pinned to **200x50**; the per-pane cell dimensions each
  scenario produced are listed with it.
- 15s sample window per scenario, after a warmup, paced at one frame per
  16 ms.
- Real detached daemon over a real unix socket, real PTYs. Frames go to a counting
  sink rather than a TTY: writing to a terminal measures the terminal.
- **Full UI drawn**: sidebar (22 columns), tab bar, status bar. `phases/archive/PHASE-4.md` criterion 7
  asks for this specifically, so the config is pinned in the benchmark rather than
  inherited from whoever runs it. Panes therefore get 178 of the 200 columns and
  48 of the 50 rows.
- Node v22.1.0, darwin/arm64.

## Acceptance criteria

- **Criterion 7 — 15-pane p99 frame time under 16 ms: PASS.**
  Measured 3.24 ms at 8x 43x10, 6x 42x10, 42x22.
- **Criterion 8 — hidden panes measurably cheaper: PASS.**
  Same fifteen flooding PTYs in the same daemon either way; only visibility differs.
  Snapshots pulled per frame: 11.4 visible against
  0.8 hidden (15.0x).
  Bytes to the terminal: 117.8 KiB/s against
  2.2 KiB/s. Daemon→client:
  1.1 MiB/s against 577.5 KiB/s (1.9x).

  Paint time moves less than those ratios — 0.31 ms hidden
  against 0.37 ms visible — and the reason is worth stating
  rather than hiding: hiding panes here means zooming, so the one surviving pane grows
  from 8x 43x10, 6x 42x10, 42x22 to 176x46 and blits roughly as many
  cells as the fifteen small ones did. The saving the clock does show is the fourteen
  snapshot round trips and the fourteen blits that no longer happen; what replaced them
  is one bigger pane.

## Criterion 6 — does detection move frame time?

Three passes, back to back, on an otherwise idle machine, alternating the agent
detection poll on and off (`LEAP_CHORUS_DETECT_INTERVAL_MS=0`). The committed run
above is pass 3, with detection live.

| Scenario | ON (pass 1) | OFF (pass 2) | ON (pass 3) |
|---|---|---|---|
| Single active | 2.44 ms | 2.33 ms | 2.59 ms |
| **Realistic 15** | **3.11 ms** | **3.45 ms** | **3.24 ms** |
| Stress, visible | 7.21 ms | 6.15 ms | 6.12 ms |
| Stress, 14 hidden | 6.98 ms | 6.61 ms | 6.73 ms |

frame p99. **PASS: detection does not measurably move frame time.** The reasoning is
the bracketing rather than the differences: in every scenario the two detection-*on*
passes fall either side of the detection-off one, or differ from each other by more
than they differ from it. The ON–ON spread (up to 1.09 ms at Stress-visible) is larger
than any ON–OFF gap, which is the definition of a difference below the noise floor.
p50 at fifteen panes is flatter still — 1.80 / 1.84 / 1.81 ms.

That is the expected result rather than a lucky one. The poll runs at 750 ms against a
`ps` snapshot shared by every pane and cached for 500 ms, and it lives in the *daemon*,
off the client's render path entirely. The only way it could reach frame time is by
starving the daemon of CPU while a client waits on `session.snapshot`.

### Two contaminated attempts, recorded

The first two attempts at this table produced "detection off" columns *slower* than
"detection on" in every scenario — which detection cannot cause, and which is the tell
that the measurement was wrong rather than the result surprising.

1. The test suite was running alongside the benchmark.
2. An orphaned daemon from an earlier packaged-app probe had been running for 75
   minutes, still holding fifteen flooding PTYs. It survived because a detached daemon
   is *supposed* to; there was no command to stop one, which is why
   `leap-chorus kill-server` now exists.

Do not run anything alongside this benchmark. Two phases have now produced junk
numbers this way.
